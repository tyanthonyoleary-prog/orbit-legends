# Collaborating on Orbit Legends

Two people (and their Claudes) work on this repo from different machines. Follow these
rules and you'll never overwrite each other's work.

Repo: https://github.com/tyanthonyoleary-prog/orbit-legends

## The mental model (read this once)

- **The source of truth is the Lua files in `src/`.** Nothing else.
- **Rojo builds those files into `OrbitLegends.rbxlx`**, the place you actually open in
  Roblox Studio. The `.rbxlx` is a *build artifact* — it is **git-ignored on purpose** and
  never committed. Everyone rebuilds their own copy from `src/`.
- The whole game world (station, asteroids, ships, UI) is generated by code at runtime, so
  there are no uploaded assets to sync — just code.

## The three golden rules

1. **Pull before you start.** `git pull` so you begin from the other person's latest.
2. **One feature = one branch = one Pull Request.** Never commit features straight to `main`.
3. **Don't both edit the same file at the same time.** Split work by system (see below).

## Daily workflow

```bash
# 1. Start from the latest main
git checkout main
git pull

# 2. Make a branch for what you're working on
git checkout -b feature/home-bases      # use a short, descriptive name

# 3. Work. Edit files in src/. Test by rebuilding:
#    Windows: double-click build-and-open.cmd
#    Mac/Linux: rojo build -o OrbitLegends.rbxlx   (then open it in Studio)

# 4. Commit your work (small, frequent commits are good)
git add -A
git commit -m "Add home-base storage building"

# 5. Push your branch and open a Pull Request
git push -u origin feature/home-bases
#    Then go to GitHub and click "Compare & pull request".
#    The other person (or their Claude) reviews, then merges into main.

# 6. After it's merged, clean up
git checkout main
git pull
git branch -d feature/home-bases
```

## Building & testing

- **Windows:** double-click `build-and-open.cmd` — it rebuilds the place from `src/` and
  opens it in Roblox Studio. Press Play (F5) to test. For PvP, use Test ▸ Clients = 2.
- **Mac/Linux:** install Rojo (`rojo` via [rokit/aftman](https://rojo.space)), run
  `rojo build -o OrbitLegends.rbxlx`, then open the file in Studio. (The bundled
  `tools/rojo.exe` is Windows-only — ignore it on other platforms.)
- **Saving/DataStores:** progress only persists once the place is published to Roblox with
  *Studio Access to API Services* enabled. In local testing it runs in no-save mode — that's
  expected.

## How the code is organized (so you know where to work)

- `src/shared/GameConfig.lua` — **every tunable number** lives here: ship stats, weapons,
  resource values, asteroid fields, upgrade curves, prices, safe-zone radius. Balance changes
  almost always go here.
- `src/shared/` — code shared by client + server (`Remotes`, `ShipStats`, `GameConfig`).
- `src/server/` — server-authoritative systems (data, world gen, ships, mining, combat,
  economy, upgrades). Game logic and anything security-sensitive goes here.
- `src/client/` — what each player sees/controls (flight, HUD, nameplates, station UI).

## Suggested division of work (post-MVP roadmap)

These barely overlap, so pick different ones and you'll rarely touch the same files:

| Feature | Mostly touches |
|---|---|
| Home-world bases | new `src/server/BaseSystem.lua`, `WorldGen.lua`, a base UI |
| Weapon-swap shop | `StationUI.lua`, `GameConfig.Weapons` (weapons already defined) |
| Missions | new `src/server/MissionSystem.lua`, `StationUI.lua` |
| Guilds/factions | new `src/server/GuildSystem.lua`, data schema |

If you must change a shared file (like `GameConfig.lua` or `Remotes.lua`), give the other
person a heads-up so you can merge cleanly.

## If you hit a merge conflict

It just means you both changed the same lines. Don't panic:

```bash
git pull                      # Git marks the conflict in the file
# Open the file, find the <<<<<<< / ======= / >>>>>>> markers,
# keep the correct combination of both sides, delete the markers.
git add <the-file>
git commit                    # finishes the merge
```

When in doubt, ask your Claude — paste the conflicted section and it'll sort it out.

## Working with Claude on each side

- Each person runs their own Claude on their own checkout. Edits, builds, and PR reviews
  happen locally per machine.
- Claude can open and review the *other* person's Pull Request directly — a good way to keep
  quality high before anything merges into `main`.
- Keep `main` always-working: only merge PRs that build and run.
